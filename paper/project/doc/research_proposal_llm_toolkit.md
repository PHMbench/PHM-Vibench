# LLM_Explainable_FD_Toolkit Research Proposal：大模型增强的可解释故障诊断工具集

> 面向后续 Agent：本文件将 LLM 工具包的研究目标拆解为可执行的技术任务，使你可以在现有代码基础上扩展功能并产出论文可用结果。

---

## 一、要解决的问题（Problem）

1. **传统可视化解释难以支撑工程沟通与决策**
   - 热力图、特征重要性曲线等虽然可视化直观，但工程师仍需自行解读，对理解和沟通存在门槛。  
   - 现有解释很少直接回答「为什么是这个故障？应该怎么处理？」等高层问题。

2. **LLM 与故障诊断系统之间缺乏深度耦合**
   - 许多 LLM 应用停留在通用问答层面，未能充分利用信号处理结果、可解释特征和知识图谱。  
   - 缺少将「模型内部行为 + 领域知识 + 用户上下文」综合输入 LLM 的系统性方法。

3. **缺乏可重复的评估框架来验证 LLM 解释的质量**
   - 如何量化“解释是否更易理解、更有用”仍不明确。  
   - 需要构建一套从离线指标到用户研究的完整评估方案。

---

## 二、研究内容（Research Content）

1. **多层 LLM 增强解释架构设计**
   - 信号处理层：来自主仓库和 Explainable_FD_Toolkit 的结构化解释结果。  
   - 知识增强层：故障知识图谱、术语映射和上下文信息。  
   - LLM 集成层：多提供方 LLM 接口、Prompt 管理、响应解析。  
   - 交互接口层：对话代理、查询理解与反馈收集。

2. **解释生成与对话机制研究**
   - 将模型输出与解释结果转化为 LLM 的输入模板（prompts）。  
   - 设计多轮对话流程：从初始诊断 → 追问 → 澄清 → 建议。  
   - 在不同任务（解释、复核、建议、风险提示）中合理调度 LLM 能力。

3. **解释质量与用户体验评估**
   - 构建用户代理指标（例如自动评分规则）评估：准确性、完整性、可理解性。  
   - 规划小规模用户研究，收集工程师的主观评分与反馈。  
   - 分析 LLM 幻觉风险与缓解策略。

## 三、技术路线（Technical Route）

> 重点是告诉后续 Agent：在哪些模块补充什么功能，以及如何通过已有脚本运行实验。

### 3.1 代码结构与职责

核心目录：`Paper/LLM_Explainable_FD_Toolkit/code/llm_explainable_toolkit/`

- `core/`：  
  - `diagnostic_system.py`：整体诊断与解释系统的主入口（接收输入 → 调用模型与 LLM → 返回解释）。  
  - `explainer.py`：定义 LLM 增强解释器接口和主流程。  

- `interactive_interface/`：  
  - `conversation_agent.py`：对话代理，负责对话状态管理、轮次控制和用户意图识别。

- `knowledge_enhancement/`：  
  - 预留知识增强模块接口（可与 Explainable_FD_Toolkit 中的知识图谱集成）。

- `llm_integration/`：  
  - 提供多 LLM 后端统一接口（如 OpenAI、本地模型等；当前为占位，后续 Agent 可实现）。

### 3.2 数据流与信息融合

1. **输入阶段**  
   - 原始信号或特征通过主仓库模型 → 得到诊断结果和可解释性结果（热力图、重要特征等）。  
   - 将这些结果转换为结构化中间表示（例如 JSON 对象或 Python dict）。

2. **知识增强阶段**  
   - 使用 Explainable_FD_Toolkit 的知识图谱和术语映射，将特征/频段/算子映射到工程语义。  
   - 生成包含：故障类型、症状、可能原因、相关工况的结构化知识片段。

3. **LLM 提示构建与调用**  
   - 设计 prompt 模板，将模型解释 + 知识片段 + 用户问题融合：  
     - 背景描述：设备类型、工况、历史诊断记录。  
     - 模型证据：关键频段、故障特征、模型置信度。  
     - 任务指令：解释、对比、建议、风险提示等。  
   - 调用指定 LLM（由配置文件控制），得到自然语言解释与结构化输出（如 JSON slot）。

4. **输出与对话管理**
   - 将 LLM 输出加工为：
     - 简明解释摘要；
     - 详细技术说明；
     - 建议与注意事项。
   - 通过 `conversation_agent.py` 管理多轮对话，支持追问与澄清。

### 3.3 输入解释来源说明（统一 Baseline 集成）

#### 3.3.1 统一 Baseline 集成架构

本 LLM 解释性工具包与团队开发的统一故障诊断 baseline 深度集成，完整数据流程如下：

```
统一 Baseline 模型 → Explainable_FD_Toolkit → 国产 LLM API → 自然语言解释
        ↓                     ↓                    ↓              ↓
TSPN/Fusion1D2D         结构化解释数据      Deepseek/GLM-4    中文优化输出
性能基准: 92-97%         SignalData格式     高性价比API     本土化支持
```

#### 3.3.2 模型输出与 LLM 输入字段映射

| 统一 Baseline 输出 | 数据格式 | LLM 输入字段 | 说明 | 数据来源 |
|-------------------|----------|-------------|------|----------|
| 故障分类结果 | int (0-4) | fault_type | 故障类型代码 | TSPN/Fusion1D2D |
| 置信度分数 | float (0-1) | confidence | 诊断置信度 | 所有模型 |
| 注意力权重 | array | attention_weights | 关键特征标识 | Fusion1D2D |
| 统计特征 | array | statistical_features | 时频域特征 | TSPN |
| 原始信号 | array(4096,) | raw_signal | 振动数据 | 数据集 |
| 模型名称 | str | model_name | 诊断模型名称 | 配置文件 |
| 设备信息 | dict | equipment_info | 设备和工况信息 | 数据集元数据 |

#### 3.3.3 国产大语言模型集成优势

**Deepseek 集成特点**：
- **成本效益**: API 调用成本仅为 OpenAI 的 20%
- **中文理解**: 针对中文故障诊断术语优化
- **API 兼容**: 完全兼容 OpenAI 格式，集成简单
- **服务稳定**: 国内网络环境访问延迟低

**GLM-4 集成特点**：
- **技术理解**: 智谱 AI 专业支持，技术文档理解能力强
- **行业适配**: 针对工业场景专门优化
- **持续更新**: 模型功能不断完善，支持定制化
- **专业可靠**: 企业级服务保障


```python
# 使用 Deepseek 生成解释

    fault_data=baseline_result,
    style="detailed",
    provider="deepseek"
)
```

## 五、讨论（Discussion）

1. **LLM 幻觉与安全性**
   - 必须明确：LLM 不参与“预测标签”，而是在模型已有结果基础上生成解释与建议。  
   - 讨论如何通过硬性约束（如只允许引用给定证据）和格式检查减少幻觉影响。

2. **领域知识覆盖缺失的问题**
   - 现有知识图谱和术语库是否足以覆盖目标设备与故障类型？  
   - 探讨如何通过增量维护和专家标注逐步完善知识层。

3. **泛化性与可移植性**
   - 在不同设备与行业（风电、化工等）间迁移时，哪些部分可复用，哪些部分需重新定制？  
   - 讨论 Prompt 模板与知识层的可配置性。

4. **与 Neuralsymbolic_theory 的关系**
   - LLM 解释可以视为神经-符号-语言三层的一部分输出。  
   - 探究如何将 LLM 输出与形式化符号表示（逻辑规则、图结构）统一起来。

## 七、Agent 关键结果目标（建议作为论文最小支撑集）

> 后续 Agent：LLM 工具包的论文说服力，核心在于“解释是否更好用 + 对诊断是否有帮助”，建议优先保障以下结果。

- **解释质量与可理解性主表**  
  - 内容：传统可视化解释 + 文本说明 vs LLM 解释（基础/知识增强）的专家评分与模拟用户评分。  
  - 用途：直接回答“LLM 解释是不是比传统解释更容易被工程师接受”。

- **诊断性能与效率影响表**  
  - 内容：有/无 LLM 对话辅助时，诊断准确率、任务完成时间、错误率、用户满意度的对比。  
  - 用途：证明对话式解释不仅“好看”，而且实际提升诊断过程质量。

- **典型对话与解释案例集**  
  - 至少 3–5 条完整对话：从模型结果 → LLM 解释 → 用户追问 → 进一步澄清/建议。  
  - 用途：作为论文中的示例对话，以及演示/附录材料。

- **幻觉与安全性分析结果**  
  - 内容：在有/无约束策略下，LLM 解释中出现事实错误或越权推断的比例与类型分析。  
  - 用途：证明你已经认真考虑并实测了 LLM 风险，而不是“盲信大模型”。
