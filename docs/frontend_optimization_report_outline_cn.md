# Frontend Optimization Report Outline (CN)

本文件用于“前端需要优化的内容报告”的标准提纲。

目标不是生成一份泛泛的 UI 美化清单，而是围绕当前仓库的维护主线
`frontend/streamlit_app.py` + `frontend/console/`，系统梳理研究控制台还需要
优化的内容、优先级、约束、验证方式和后续路线。

写作要求：

- 以当前 `frontend/` 主线为对象，不回到 `frontend/legacy/` 做主叙事。
- 以“研究控制台”而不是“营销化 dashboard”为定位。
- 每一级标题都必须回答一个明确问题，不能只有标题没有内容要求。
- 每个四级标题都要写成可填充的“所需内容”说明，便于直接扩写成正式报告。

# 1. 报告总览

- 本章需回答：为什么现在要重新梳理前端优化内容，这份报告服务谁，最终想把前端提升到什么状态。

## 1.1 报告背景

- 本节需说明当前仓库前端所处阶段，以及这次重梳理是如何被触发的。

### 1.1.1 当前前端所处阶段

- 本小节需说明当前前端不是独立产品前端，而是 PHM-Vibench / PHMfactory 的维护主线控制台。

#### 1.1.1.1 所需内容

- 明确当前维护主线位于 `frontend/`，入口是 `frontend/streamlit_app.py`。
- 明确 `frontend/console/` 是维护面，`frontend/pages/` 是 Streamlit multipage 包装层。
- 明确 `frontend/legacy/` 只是历史归档，不再作为主线优化对象。
- 明确 CLI 仍是唯一权威执行入口：`python main.py --config ...`。
- 用一句话概括当前前端角色：研究控制台、实验控制面、证据链查看器。

### 1.1.2 本次重梳理的触发原因

- 本小节需说明为什么已有前端优化还不够，需要进一步系统梳理。

#### 1.1.2.1 所需内容

- 说明此前优化点分散，难以形成完整路线图。
- 说明页面、数据、交互、视觉、文档之间还缺少统一的优化清单。
- 说明需要把“性能、结构、表达、维护性”放到同一个报告里统一审视。
- 说明后续若要演进到更强的品牌化前端，必须先把当前控制台问题收口清楚。

## 1.2 报告目标

- 本节需说明这份报告最终要产出什么，不产出什么。

### 1.2.1 总目标

- 本小节需给出一条总目标陈述，作为整份报告的判断基线。

#### 1.2.1.1 所需内容

- 用一句话写清总目标，例如：将前端从“可用的 Streamlit 控制台”提升为“低认知负担、可验证、可扩展的研究控制面”。
- 明确目标是提升控制体验与可维护性，不是做营销站点。
- 明确目标是支撑实验流程，不是替代 CLI 执行链。

### 1.2.2 具体目标

- 本小节需把总目标拆成可观察的子目标。

#### 1.2.2.1 所需内容

- 分别列出性能、信息结构、交互流畅度、证据链可见性、视觉统一性、维护性六个子目标。
- 每个子目标都要写成“当前不足 + 期望状态”的形式。
- 每个子目标都要有可验证结果，例如页面启动时间、点击路径、错误提示清晰度、artifact 可达性。

## 1.3 报告适用对象

- 本节需说明谁会使用这份报告，以及不同读者关心什么。

### 1.3.1 读者分层

- 本小节需区分维护者、实现者、使用者与后续架构设计者。

#### 1.3.1.1 所需内容

- 说明仓库主维护者关注优先级和演进路径。
- 说明前端实现者关注页面边界、适配层职责、状态模型和验证要求。
- 说明实验使用者关注是否更快完成 compose / inspect / launch / compare / trace。
- 说明后续独立 Web shell 设计者关注哪些结论可直接继承。

- 说明 `frontend/console/pages/` 负责页面渲染逻辑。
- 说明 `frontend/console/theme.py` 与 `frontend/console/state.py` 分别承担视觉和状态职责。
- 说明 `frontend/pages/` 是 Streamlit 的多页面桥接层，而不是业务逻辑层。

### 2.1.2 多页面结构与页面职责

- 本小节需说明页面是否真的形成研究控制台，而不是分散的工具页。

#### 2.1.2.1 所需内容

- 说明每个页面的输入是什么、输出是什么、用户完成的动作是什么。
- 指出是否存在职责重叠、页面间跳转负担、信息重复或缺失。

## 2.2 运行与数据链路现状

- 本节需说明前端如何与 CLI、配置系统和运行产物连接。

### 2.2.1 执行链路

- 本小节需说明前端的动作边界。

#### 2.2.1.1 所需内容

- 说明前端如何从 config 选择走到 preflight，再走到 CLI launch。
- 说明前端不执行训练逻辑本身，只生成并调用命令。
- 说明 session state 在页面之间承担什么角色。
- 指出当前链路中可能存在的中断点、误解点或状态不同步问题。

### 2.2.2 Artifact 与证据链

- 本小节需说明前端看见的 run 证据到底有哪些。

#### 2.2.2.1 所需内容

- 列出 `config_snapshot.yaml`、`test_result_*.csv`、`artifacts/manifest.json`、`figures/`、`logs/**/metrics.csv`、`predictions.npz`。
- 说明这些对象如何被 Workbench、Runs、Compare、Artifacts 页面消费。
- 指出哪些证据对象已是一等对象，哪些还只是“能看到文件”而不是“能理解内容”。

## 2.3 现阶段体验状态

- 本节需区分“已经优化过的内容”和“仍然需要继续优化的内容”。

### 2.3.1 已完成或已改善的内容

- 本小节需说明前端现阶段已经取得的结构性进展。

#### 2.3.1.1 所需内容

- 说明主线已统一到 `frontend/`。
- 说明 Registry 已从模块级重导入改为懒加载。
- 说明 Compose 已改成显式 preflight，而不是每次输入自动重算。
- 说明首页与页面导入链已经做过收口。
- 说明哪些问题已经不再是当前主矛盾。

### 2.3.2 当前仍存在的问题

- 本小节需写具体问题，不要只写“还可以更好”。

#### 2.3.2.1 所需内容

- 按性能、交互、视觉、信息结构、证据链表达、文档一致性六个维度写问题。
- 每个问题都写成“现象 + 影响 + 可能成因”的形式。
- 问题要贴当前前端，不要泛化为一般性产品建议。

# 3. 前端需要优化的核心内容

- 本章需回答：到底要优化什么，优化的对象如何分层。

## 3.1 信息结构层

- 本节需聚焦页面组织和信息优先级，而不是视觉样式。

### 3.1.1 首页定位与首屏结构

- 本小节需回答 Workbench 是否已经承担真正的控制台首页职责。

#### 3.1.1.1 所需内容

- 评估首页是否优先呈现当前 protocol、recent runs、artifact 状态、quick actions。
- 评估首页卡片与表格的优先级是否合理。
- 评估“首次进入用户”是否能迅速知道下一步要做什么。
- 写出建议保留项、应降级项、应新增项。

### 3.1.2 页面边界与信息分配

- 本小节需回答六个页面之间的边界是否清晰。

#### 3.1.2.1 所需内容

- 检查 Compose 是否只承担 compose / preflight / launch。
- 检查 Runs 与 Artifacts 是否职责清晰分离。
- 检查 Compare 是否只做公平比较而不是兼做 run 详情。
- 检查 Registry 是否承担“查看已注册组件”而不是“配置入口”。
- 给出页面职责收口建议。

## 3.2 交互流程层

- 本节需聚焦用户点击路径和状态反馈。

### 3.2.1 Compose 主路径

- 本小节需说明 Compose 的关键交互点是否足够顺滑。

#### 3.2.1.1 所需内容

- 分析 config 选择、override 编辑、preflight、launch 的顺序是否自然。
- 说明按钮启用/禁用条件是否透明。
- 说明输入变化后 preflight 失效逻辑是否容易理解。
- 说明错误提示是否能帮助用户回到正确路径。

### 3.2.2 Runs / Compare / Artifacts 主路径

- 本小节需说明实验查看与比较路径是否低认知负担。

#### 3.2.2.1 所需内容

- 说明用户如何从 recent runs 进入单 run 查看。
- 说明用户如何选择多个 run 进入 compare。
- 说明 protocol mismatch 提示是否足够直观。
- 说明 artifact 预览是否符合“先选对象，再看证据”的流程。

## 3.3 性能与稳定性层

- 本节需聚焦“丝滑度”的硬问题，而不是抽象体验描述。

### 3.3.1 启动、导入与切页性能

- 本小节需说明哪些地方还可能拖慢使用。

#### 3.3.1.1 所需内容

- 说明入口导入耗时、页面初始渲染耗时、切页时的数据加载情况。
- 说明 adapter 层是否仍有不必要的全量扫描和重计算。
- 说明哪些数据适合 summary-first，哪些必须 detail-on-demand。
- 给出建议度量口径，例如冷启动耗时、切页感知延迟、Compare 加载时间。

### 3.3.2 状态一致性、错误恢复与空状态

- 本小节需说明前端在非理想条件下是否容易理解和恢复。

#### 3.3.2.1 所需内容

- 说明 session state 是否存在易混淆状态。
- 说明 preflight 失败、artifact 缺失、无运行记录、协议不一致时的反馈质量。
- 说明错误提示是否有下一步动作建议。
- 说明空状态设计是否能帮助用户进入下一步，而不是只显示“无数据”。

## 3.4 视觉与表达层

- 本节需聚焦视觉统一和科研语境，而不是单纯审美偏好。

### 3.4.1 主题统一性

- 本小节需检查 Instrument Noir / Editorial Lab 是否真正被一致执行。

#### 3.4.1.1 所需内容

- 检查主题色、边框、表格、按钮、Tabs、代码块、状态提示是否统一。
- 检查 serif 标题 / sans 正文 / mono 数据的分工是否稳定。
- 检查是否仍残留默认 Streamlit 风格元素。
- 指出最影响整体质感的不一致点。

### 3.4.2 科研控制台表达方式

- 本小节需检查页面是否真的像研究控制台，而不是参数表单工具。

#### 3.4.2.1 所需内容

- 检查标题、文案、指标摘要是否围绕 protocol、run、artifact、compare 组织。
- 检查是否存在 SaaS 化、营销化、过度装饰化表达。
- 检查数据是否可读、是否便于快速判断实验状态。
- 给出更适合科研语境的表达原则。

## 3.5 可维护性层

- 本节需聚焦未来继续改这个前端时会不会越来越乱。

### 3.5.1 代码边界与模块职责

- 本小节需回答当前实现边界是否稳固。

#### 3.5.1.1 所需内容

- 检查 pages 是否只负责页面渲染。
- 检查 adapters 是否只负责取数和转换。
- 检查 theme 与 state 是否保持单一职责。
- 指出仍可能出现职责混杂的点。

### 3.5.2 文档、约定与协作成本

- 本小节需回答维护者接手时是否容易理解和扩展。

#### 3.5.2.1 所需内容

- 检查 `frontend/README.md`、`docs/app_usage.md`、`docs/README.md` 是否一致。
- 说明前端运行方式、目录职责、artifact 契约是否足够明确。
- 说明后续新增页面或 adapter 时应遵守什么约定。
